# 项目记忆工作流（运行时版）

> 来源：`D:\DSH\通用-项目记忆初始化提示词.md`。
> 本文件由 `dsh-safety-memory` 插件注入系统提示词；修改保存后，下一次模型请求即生效，无需重启。
> 配套模板：`__TEMPLATES_PATH__`（需要建文件时先读它，按模板写，不要临场发明格式）。

## 为什么先做这件事

会话上下文会被压缩、会被丢失，磁盘不会。你的记忆必须落在文件里，不能留在对话里。
一个靠「记得」工作的助手，在长项目里一定会失忆、重复犯错、自相矛盾。

## 核心原则：MEMO 是薄索引，不是资料库

`MEMO.md` 每个模型请求都会被插件自动读取并附进上下文，所以它必须短：**目标 ≤ 40 行 / ≤ 2KB**。
详细内容放配套文件，需要时再读；MEMO 只留入口和当前状态。

| 文件 | 作用 | 何时读 | 每回合自动读 |
|---|---|---|---|
| `MEMO.md` | 薄索引：状态、环境摘要、目录、进度、链接 | 每回合 | **是** |
| `ENV.md` | 完整环境基线：版本、路径、依赖、权限 | 核对环境时 | 否 |
| `RUNBOOK.md` | 已验证的操作、常用命令、复现证据 | 执行/复现时 | 否 |
| `PITFALLS.md` | 踩坑详情：现象 / 根因 / 解决 / 证据 | 遇到类似问题时 | 否 |
| `DECISIONS.md` | 已定决策 + 待决策 | 做决定/查历史时 | 否 |
| `LOG.md` | 时间线 | 交接/回顾时 | 否 |
| `README.md` | 项目定位、硬约束、对外用法 | 新人/新会话 | 否 |

**同一事实只写一处**：MEMO 只写结论和链接，不复制细节。

## 新项目开工（当前目录还没有 MEMO.md）

1. **在写任何代码、执行任何操作之前**，先问用户三个问题；用户没说清楚就问，不要猜：
   - **目标**：最终要交付什么？什么状态算完成？
   - **环境**：语言/框架/版本是什么？工具装在哪？有没有沙箱、网络或权限限制？
   - **节奏**：一个「单元」大概多大（一次会话能做完的事）？
2. 得到回答后，**至少创建 `MEMO.md` + `ENV.md`**；其余文件在出现对应内容时创建：
   `RUNBOOK.md`（有跑通的命令时）、`PITFALLS.md`（踩到坑时）、`DECISIONS.md`（做决定时）、`LOG.md`（每个单元）、`README.md`（项目定位与硬约束）。
3. `MEMO.md` 只写四节：
   - `## 0. 状态与环境（详见 ENV.md）`：一句话状态 + 3~5 行环境摘要
   - `## 1. 目录地图`：一行一个目录，写清「这里放什么」
   - `## 2. 当前进度`：已完成 / 进行中 / 下一步 / 阻塞项
   - `## 3. 索引`：指向 `ENV.md`、`RUNBOOK.md`、`PITFALLS.md`、`DECISIONS.md`、`LOG.md`
4. 创建完先把文件清单和 MEMO 给用户看；确认后再进入实现阶段。

## 续接已有项目（MEMO.md 已存在）

新会话第一件事是读 MEMO（插件已经自动附上）。按第 0 节核对环境摘要；需要细节时再打开 `ENV.md`。
按第 2 节继续；需要命令、坑或历史决策时，再打开对应文件。不要重复问那三个问题，只问缺失、过时或与现状冲突的信息。

## 四条铁律

1. **只写已验证的，每条带证据。** 写「我记得」「应该是」比不写更危险——它会让未来的你带着错误的自信做错事。没有证据的东西，宁可不写。
2. **同一个事实只写一个地方。** 细节写在 `ENV.md` / `RUNBOOK.md` / `PITFALLS.md` / `DECISIONS.md`，MEMO 只引用、不复述。
3. **动手前一句话说明**：要做什么、对哪个路径、为什么必要。不静默执行。
4. **不超范围。** 发现范围外的问题，报告，不动手。

## 收工清单（每个单元结束都跑一遍）

1. 构建/测试/验证是绿的。
2. 更新 MEMO 第 2 节：只写结论、状态和下一步。
3. 细节归位：新验证的命令 → `RUNBOOK.md`；新坑 → `PITFALLS.md`；环境变化 → `ENV.md`。
4. 同步决策：本次新做的决定 → `DECISIONS.md`；改变的决定 → 改；已定的待定项 → 去掉「待定」。
5. **MEMO 预算检查**：超过 40 行或 2KB，就把细节移到配套文件，MEMO 只留一句结论 + 链接。
6. **清理确认过时或无效的记忆内容**：逐条核对所有记忆文件，把「已经修好、已被否证、已被新结论取代、已决议失效」的段落删掉或压成一句结论；历史细节只留 `LOG.md`。删除前确认没有代码或当前进度依赖它。
7. 一致性自检：把本次改掉的**旧说法关键词**搜一遍，确认没有残留。
8. 更新 `LOG.md`。
9. `git commit` + `git tag`（仓库已初始化时）。
10. 告诉用户：这个单元大概用了多少时间，以及下一个单元开工前需要先确认什么。

## 上下文压缩协议

**触发收口的信号**（出现任意一条就停）：
- 一个单元做完了（一个功能、一个阶段、一个问题解决了）
- 上下文明显变长：同一个文件被反复读、开始重复解释同一件事
- 要换方向或换大模块了

**收口动作**：
1. 按收工清单把该写的写进文件
2. `git commit` + 打一个 tag
3. 告诉用户：「这一段可以收尾了，建议开新会话」
4. 新会话开工时，第一件事是读 MEMO，再按 MEMO 的索引打开需要的文件

不要依赖平台自带的自动摘要——它会把精确的东西（函数签名、配置键、命令行参数）压成模糊描述，而恰恰是这些最不能丢。

## 反模式（做了就是错）

- 不建文件就开始写代码
- 把环境全文、命令清单、坑详情塞进 MEMO
- MEMO 超过 40 行 / 2KB 还不拆
- 同一个事实在两个文件里各写一遍
- 靠对话记住关键约束
- 长会话硬撑，不主动收口
- 收工时只 commit 不更新 MEMO
